# 简历项目描述与面试材料

## 一句话版本

ShopLens 是一个面向耳机选购的可解释多模态 RAG 导购系统：用 PostgreSQL/pgvector 完成词法、文本和图片召回，用确定性硬过滤与最多四步的有界 Agent 生成可追溯推荐，并用冻结评测、故障注入和规模基准验证质量与韧性。

## 简历三条版

以下数字都限定为“24 件 CC0 Fixture / 合成规模数据”，可直接回链到报告：

- 设计 Next.js + FastAPI + PostgreSQL/pgvector + Redis 的多模态导购系统，统一 FTS、1024 维文本向量和 768 维图片向量召回，以参数化硬过滤、版本化 HNSW、RRF 与有限 Top-K 重排支持文本、纯图、图文和 2～4 商品对比。
- 构建最多 4 步的代码固定 Agent 状态机与证据 ID 协议；在 15 个确定性多轮场景、384 条结构化事实声明中实现任务/工具/引用指标 1.0000、结构化事实幻觉率 0.0000，评测实测最大 3 次工具调用。
- 冻结并扩展至 150 条文本消融，Fixture 上 RRF Recall@10 0.9821、nDCG@10 0.9464；通过缓存、固定窗口限流、有界重试/熔断、Prometheus 和 keyset 批处理加固，并在 50k 合成行上将结构化过滤/FTS/ANN 的数据库查询 P95 从 23.389/39.634/239.207 ms 降至 0.462/10.681/1.113 ms。

数字依据：`evals/reports/stage6-agent-evidence.json`、`stage8-text-ablation.json`、`stage8-performance.json`。不要删掉“Fixture / 合成 / 数据库查询”的限定词。

## STAR 1：把“会聊天”改造成可核验导购

**Situation**：普通聊天式导购会把预算、品类和 ANC 交给模型理解，且推荐理由无法定位到事实，价格和评论容易混在自然语言里。

**Task**：既保留自然语言体验，又保证硬条件绝不由模型猜测，所有事实和对比单元格可追溯。

**Action**：我把输入限制为白名单 `SearchFiltersInput`，由参数化 SQL 在所有召回通道前执行；Agent 改为最多四步的代码固定状态机，模型只能返回严格 Schema 和选择已知证据 ID。商品事实、评论和缺失值先构造成证据包，最终回答由代码渲染，再做跨商品、跨字段引用校验。前端只读结构化 `recommendations/evidence/comparison`，不从答案反向解析。

**Result**：15 个 Fixture 多轮场景任务完成率、工具选择、引用精度和覆盖率均为 1.0000；384 条结构化事实声明幻觉率为 0.0000，最大工具调用 3。数字仅证明确定性控制流和证据协议。

## STAR 2：用消融发现“更复杂并不更好”

**Situation**：加入向量、重排和图片融合后，几个手选 Demo 看起来不错，但无法说明每个组件是否真的增益。

**Task**：建立可重复的对照实验，保留失败样本，不用调标签制造提升。

**Action**：冻结阶段 3 的 30 条词法查询和阶段 4 的 18 条语义查询，阶段 8 只新增 102 条商品身份、对抗空结果和场景查询；对 lexical/dense/RRF/rerank 运行同一 150 条集，保存每条期望/返回 ID、硬条件、延迟和失败 ID。多模态也做纯图、混合去图、混合去文和完整融合四组消融。

**Result**：RRF 在当前 Fixture 上 Recall@10 0.9821、nDCG@10 0.9464，优于重排；完整图文融合 nDCG@10 0.9037，低于文字消融 0.9755。负结果促使我把后续计划改为先获得真实授权数据和独立标注，再校准权重/重排，而不是继续拟合合成集。

## STAR 3：从功能 Demo 补到可降级工程

**Situation**：远程 Embedding/Reranker/图片模型/Agent 任一超时都可能放大为全链路失败；数据库在 50k 合成行上 ANN 顺序扫描 P95 达 239.207 ms。

**Task**：让核心检索在依赖失败时仍返回，并量化数据增长后的瓶颈。

**Action**：统一四类 HTTP Provider 的超时、可重试错误、最多三次指数退避和 closed/open/half-open 熔断；Redis 缓存与限流故障 fail-open；响应暴露机器可读降级原因。用 5k/50k 基准保存索引前后 P50/P95 和完整执行计划，再增加硬过滤 covering index、FTS GIN、pgvector HNSW，并把双向量回填改为 UUID keyset 批处理。

**Result**：50k 合成行索引后结构化过滤、FTS、ANN 的 DB 查询 P95 分别为 0.462、10.681、1.113 ms；真实 Reranker 不可达时系统明确回退 RRF 并保留硬条件和商品结果。该结果不是并发压测或生产 SLO。

## 高频追问与真实取舍

### 为什么用 PostgreSQL + pgvector，不单独上 Elasticsearch 和向量数据库？

MVP 数据量和团队规模下，商品事实、硬过滤、FTS、向量和来源审计放在同一事务边界更简单，能复用 SQL 过滤并减少双写一致性问题。代价是中文分词、超大规模分片和专用向量调优能力较弱；当真实数据/并发超过单库边界时，再用双写 outbox 和离线回放拆分，而不是先引入三套存储。

### 为什么融合排名而不是直接相加相似度？

词法、文本向量和图片向量的分数不可直接比较，模型版本变化也会改变分布。RRF 只使用通道内排名，稳定、可解释、无需假装分数已校准。代价是丢失分数间距信息；获得真实独立标注后可评估学习排序或校准分数，但硬过滤仍要在通道前执行。

### 为什么不用开放式 ReAct？

导购只有检索、详情和对比等少量工具，开放循环会增加成本、延迟、提示注入面和不可预测性。固定状态机把最大步骤硬限制为 4，模型只解析 Schema/选证据。代价是任务覆盖面较窄，但失败可预测、轨迹可审计，适合高事实约束场景。

### 如何防止硬条件被模型放宽？

预算、币种、品类、ANC 等进入 `SearchFiltersInput` 白名单，转换为参数化 SQLAlchemy predicate，并在每个召回通道之前复用。只有软偏好可以排序或在响应中明确 `relaxed_preferences`；模型不能生成 SQL，也不能覆盖过滤结果。评测单独统计硬条件违反率。

### 如何降低幻觉？

把“生成答案”拆为“构造证据包 → 模型选择已知证据 ID → 确定性渲染 → 引用校验”。价格、参数、对比格来自结构化字段；描述和评论标记为非可信。未知/跨商品/字段不一致引用被拒绝，失败时退回可验证事实卡。Fixture 下的 0 幻觉只证明这一协议，不代表真实模型没有其他错误。

### 如何处理提示注入？

用户、描述、评论、图片 OCR 都是数据，不是控制指令；它们不能决定工具、SQL 或硬条件。工具集合和状态转换在代码中固定，模型响应 `extra=forbid`。真实模型接入后仍需对抗集、红队和监控，不能只靠系统提示词。

### 为什么重排和多模态反而变差？

Fixture Reranker 是确定性替身，不是真实 BGE；图片是规则化合成图，文字查询已非常明确，融合权重也未在真实分布上校准。因此负结果合理。正确做法是保留失败 ID、补授权真实数据和独立判断集，再校准；不能改标签或删查询。

### 50k 性能数字如何解释？

它是 PostgreSQL 内部查询微基准：单机、暖机三次、每项 20 次采样、合成重复向量。覆盖索引把硬过滤变成 index-only，GIN 避免 FTS 全表路径，HNSW 避免 ANN 顺序扫描。它不含 HTTP、Agent、模型网络、并发和冷缓存，因此不能称为端到端 P95 或生产 SLO。

### 缓存一致性怎么保证？

键包含规范化请求、命名空间、模型/文档版本，版本切换自然进入新键空间。默认 TTL 60 秒；当前只有离线写，导入后切换命名空间或等待 TTL。真实在线商品更新应增加事件驱动失效和数据版本水位，而不是无限缩短 TTL。

### Redis 挂了为什么 fail-open？

缓存和限流不是商品事实的权威来源。让 Redis 故障阻断全站会扩大故障半径，因此搜索继续走数据库并记录降级指标。代价是暂时失去缓存收益和限流保护，必须依靠网络入口、代理限流和告警补偿；认证/会话失败则需要更谨慎的策略。

### 为什么不用 WebSocket？

当前请求可在普通 HTTP 超时内完成，不需要双向长连接。HTTP 更容易经过代理、测试、缓存和观测。若真实模型带来流式需求，会优先考虑 HTTP SSE，同时仍让结构化最终响应和引用校验成为完成条件。

### 离生产还差什么？

账号/租户授权、HTTPS 反向代理、密钥管理、真实授权数据、真实模型质量报告、共享对象存储、数据库备份/高可用、并发与长稳压测、multiprocess 指标、跨副本熔断/限流语义、SLO/告警和安全审计。当前定位是可复现的单机工程作品，不伪装成已上线平台。

### 为什么没有导入计划中的 200 件外部商品？

数据集代码 MIT 不等于内容许可。数据卡无法给出商品、评论和图片可再分发的明确授权，所以选择延期并保留 24 件 CC0 Fixture。这个取舍牺牲了规模感，但避免了许可证和来源造假，也使评测边界清晰。

## 面试时不要说的版本

- 不说“真实 BGE/SigLIP2 达到 98%”，应说“确定性 Fixture 的 150 条回归中 RRF Recall@10 为 0.9821”。
- 不说“50k 请求 P95 1 ms”，应说“50k 合成行的 ANN 数据库查询索引后 P95 为 1.113 ms”。
- 不说“Agent 零幻觉”，应说“15 个 Fixture 场景的 384 条结构化事实声明幻觉率为 0；真实 LLM 未实测”。
- 不说“生产级高可用”，应说“单机 Compose 有健康检查、降级和观测，多副本边界已列出”。
