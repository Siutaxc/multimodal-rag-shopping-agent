# 已知限制与非目标

## 数据和质量

- 规范语料只有 24 件人工 CC0 Fixture；150 条文本查询由项目作者围绕同一语料构造，不是独立标注的开放域测试集。
- 5k/50k 数据是重复并扰动 Fixture 的合成规模数据，只验证索引和执行路径，不代表真实商品分布、并发或端到端延迟。
- 外部 200 件商品因上游数据许可证不明确而延期；没有抓取实时库存、价格或评论。
- 价格是 Fixture 中带观察时间的快照，不支持实时更新、促销、地区税费或库存同步。

## 模型和检索

- BGE-M3、BGE Reranker、SigLIP2 与 Agent 远程端点只实现了 HTTP/HTTPS 契约、超时、重试、熔断和降级，尚未用真实端点跑质量报告。
- 当前指标来自确定性 Fixture Provider。它适合 CI 和演示，但不能证明真实模型质量。
- 阶段 8 中 Reranker 没有超过 RRF；阶段 5 完整图文融合低于文字消融。负结果被保留，真实数据到位后才应校准权重和重排。
- 中文词法依赖当前受控别名/事实文档，不是通用中文分词或开放域搜索方案。

## 产品和安全

- MVP 没有账号、租户、授权、支付、订单或管理后台；不透明 `session_id` 只是隔离键，不是身份认证。
- 会话存在同一 Redis 中，知道 UUID 的客户端可以读取对应上下文；公网部署前必须增加认证、授权和租户绑定。
- 上传图片经过严格净化，但当前对象存储是单机命名卷；生产多副本需要共享对象存储、恶意内容扫描和生命周期策略。
- 评论和描述被视为非可信数据并与系统指令隔离，但真实模型接入后仍需持续对抗测试和人工红队。
- CORS 可配置，生产模板只接受明确 HTTPS 来源；项目没有内置 TLS、WAF 或反向代理。

## 一致性和韧性

- 搜索缓存默认 TTL 60 秒。离线导入后最多短暂读到旧结果，可切换 `SHOPLENS_CACHE_NAMESPACE` 或等待 TTL；当前没有在线写 API。
- Redis 缓存与限流故障采用 fail-open，以可用性优先；这意味着故障期间保护强度下降，应通过告警和网络边界补偿。
- 固定窗口限流按 API 直接看到的客户端地址计算，不直接信任 `X-Forwarded-For`；反向代理必须是唯一受信入口。
- 熔断状态保存在 API 进程内；多个 worker 或副本不会共享状态。

## 可观测性和部署

- 自建 Prometheus 累加器只适用于单 API 进程。多 worker 前必须改为 multiprocess 安全的指标库或外部聚合。
- 当前性能报告是单客户端数据库微基准，没有 HTTP 并发、长稳、容量、故障恢复时间或生产 SLO。
- Compose 生产覆盖适合单机作品部署，不提供 Kubernetes、多区域、高可用 PostgreSQL、Redis Sentinel/Cluster 或自动备份。
- 开发 trace 含检索和工具细节，生产环境固定关闭；日志刻意不记录用户查询，因此问题排查依赖 request ID 和聚合指标。
- 本轮容器构建的 `npm ci` 汇总仍报告构建依赖图中 1 个 moderate、2 个 high；没有运行破坏性 `npm audit fix --force`。公网部署前应按具体 advisory 逐项升级、重建并重新验收，且不能把 build-stage 依赖数量直接等同于最终 standalone 运行镜像暴露面。

## 明确非目标

- 不使用 WebSocket；未来若需要流式输出，优先评估基于 HTTP 的 SSE。
- 不让 LLM 生成或执行 SQL，不使用开放式无限 ReAct 循环，不让图片/OCR/评论决定硬条件。
- 不从自然语言答案反向解析商品或价格；前端始终使用结构化字段。
